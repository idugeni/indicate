# Stage 7 production-readiness remediation and release evidence

The remediation adds an RLS-safe host-discovery boundary, exact applied-migration comparison, a shared publication/public test journey, provider and Telegram-secret contracts, executable promotion evidence, broader rollback recovery, secret scanning, and PostgreSQL CI. Forced-RLS discovery, cache and credential checks, promotion wiring, and recovery-family coverage are materially improved. Shipping remains blocked by the confirmed findings below. **Watch for:** **[critical, confirmed]** arbitrary recursive deletion through `STAGE7_EVIDENCE_DIR`; **[high, confirmed]** globally duplicated region IDs break the live PostgreSQL contract; **[high, confirmed]** promotion accepts incomplete or contradictory evidence; **[high, confirmed]** R2 data-plane credentials are never exercised.

**Verdict**: NEEDS_CHANGES

## High-level view

The new `SECURITY DEFINER` function caps requests at 100 exact normalized hosts, fully qualifies tenant tables, fixes its search path, revokes public execution, and leaves direct table reads behind forced RLS. The runtime adapter compares all 13 applied migration records and CI invokes a Stage 7 PostgreSQL contract, but **[high, confirmed]** that contract reuses globally unique region IDs across three organizations and fails during setup.

The acceptance matrix starts with no public articles, publishes nine targets into one Stage 4 repository, reloads visibility from that state, injects a foreign cache entry, and checks own versus foreign API credentials. **[high, confirmed]** its public projection is a test-only repository rather than the deployed Drizzle Stage 5 path, so the evidence does not establish the production persistence journey.

The provider contract covers Cloudflare, Vercel, R2 management state, Upstash, Supabase Auth, Telegram, DNS, and HTTPS, and the emitted reports contain neither secrets nor tenant identifiers. **[high, confirmed]** it does not use the R2 S3 credentials that production media uses; **[medium, confirmed]** the two-request Telegram challenge can self-rate-limit under valid configuration.

`release:stage7` gathers quality, acceptance, and readiness artifacts and calls `decidePromotion`; rollback tests drive all seven named recovery families through application reconcilers. **[critical, confirmed]** the evidence directory is destructively reset without containment, and **[high, confirmed]** evidence parsing trusts summary booleans instead of complete, internally consistent reports.

The migration manifest detects missing, reordered, and mismatched database records, and the scanner covers several new secret-bearing artifact types. **[medium, confirmed]** local migration “checksums” are labels rather than content fingerprints; **[medium, confirmed]** the scanner excludes the entire negative-fixture tree and omits common environment/key-store formats.

## Caller-selected evidence cleanup can delete the repository or unrelated data

**[critical, confirmed]** `run-stage7-release.mjs` resolves `STAGE7_EVIDENCE_DIR` against the repository and immediately calls recursive forced removal. Absolute paths are accepted by `resolve`, `.` resolves to the repository root, and `..` resolves to its parent; a typo or caller-controlled value can erase the checkout or any writable directory before a gate runs (`scripts/run-stage7-release.mjs`, lines 5–8).

Restrict evidence to a dedicated child of the repository, reject absolute paths, traversal, the repository root, ancestors, and symlinked parent components, and remove only known artifact files. Add subprocess tests for `.`, `..`, absolute paths, and symlink traversal without exercising destructive targets.

## Promotion trusts summary booleans instead of complete evidence

**[high, confirmed]** the evidence validators require only `ready`, `requiredSchemaVersion`, and an array named `checks`, or `accepted`, `scenarioCount`, and an array named `failures`. `decidePromotion` trusts `ready: true` and `accepted: true`; an empty readiness check list or an acceptance artifact with non-empty failures can authorize promotion with the expected diagnostics (`scripts/decide-stage7-promotion.ts`, lines 10–20; `src/application/stage7/release-gate.ts`, lines 27–38). The unit test itself models successful readiness with an empty check list.

Validate every readiness check name exactly once, require all checks to be passed/ready, require schema version 13, require acceptance failures to be empty when accepted, and reject contradictory summaries. Derive summary booleans from validated details, then test malformed, truncated, duplicate, contradictory, and stale evidence.

## Shared Stage 7 region IDs prevent the live PostgreSQL contract from starting

**[high, confirmed]** `createStage7ReadinessFixture` derives each region UUID only from the external key and shares the same three region objects across every root (`src/domain/stage7/readiness-fixtures.ts`, lines 31–34). The live contract inserts those IDs once per organization (`tests/integration/stage7-postgres-live.integration.test.ts`, lines 49–53), but the schema has a global `regions_id_unique` constraint (`drizzle/0000_stage2_core_schema.sql`, lines 337–350). Setup fails on the second root, so CI cannot prove runtime-role discovery or the applied manifest.

Scope region IDs by root/organization while preserving common external keys and slugs, and assert all nine row IDs are globally distinct before insertion. Keep the direct-table RLS and bounded-function assertions after fixing the fixture.

## Test-only public projection stops short of deployed persistence

The matrix now causally connects public visibility to published `articleSites` in the same `InMemoryStage4Repository`, sends a foreign entry through `PublicContentService`, and compares own and foreign API-key access. **[high, confirmed]** `Stage7SharedJourneyRepository` still lives in `src/infrastructure/testing/stage5-fixture.ts` and synthesizes articles instead of running `DrizzleStage5Repository.loadPublicSite`. It can pass while the production query, tenant transaction, site-settings joins, region filter, or migrated schema is broken.

Run all nine scenarios against one migrated PostgreSQL dataset through `DrizzleStage4Repository`, the worker, exact-host resolution, `DrizzleStage5Repository`, and the real composition boundary; retain the deterministic matrix as fast coverage.

## Readiness can pass with unusable R2 media credentials

**[high, confirmed]** the R2 readiness probe authenticates only to Cloudflare’s management API with `CLOUDFLARE_API_TOKEN`, checking bucket existence and public-domain state (`src/infrastructure/deployment/production-readiness-adapter.ts`, lines 104–145). Production media uses `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` through `R2ObjectStorageAdapter`, but readiness neither applies production-strength validation to them nor exercises them. A private bucket with stale S3 credentials passes while uploads, reads, cleanup, and publication media fail.

Add a non-mutating `HeadBucket` data-plane probe using the production R2 adapter and production-bounded R2 credentials. Extend the provider contract to distinguish management-plane privacy from S3 credential health without logging SDK errors or credential-bearing URLs.

## Telegram secret challenge can consume its own valid allowance

**[medium, confirmed]** the adapter makes two requests from the same Cloudflare source identity—one correct secret and one mismatch—while the route allows `Math.min(10, RATE_LIMIT_WEBHOOK_ALLOWANCE)`. Valid configuration permits an allowance of one, making the mismatch probe rate-limited and readiness always fail; with a larger allowance, the sixth check in one window fails after five checks consume ten slots (`app/api/webhooks/readiness/telegram-secret/route.ts`, lines 26–39; `src/infrastructure/deployment/production-readiness-adapter.ts`, lines 160–179).

Guarantee one atomic accepted/rejected verification or redesign this as a single authenticated challenge result without secret-derived output. Test allowance one, repeated checks, mismatch, limiter outage, missing edge proof, and separation from the real webhook rate key.

## Migration labels do not fingerprint reviewed SQL

**[medium, confirmed]** applied rows are compared in exact version/name/checksum order, closing the prior `max(version)` gap. Local validation calls values such as `drizzle-0000` checksums and only searches concatenated SQL for matching insert tuples (`src/domain/stage7/migration-manifest.ts`, lines 8–21; `src/infrastructure/deployment/production-readiness-adapter.ts`, lines 67–86). Editing a migration while retaining its marker, or moving markers between files, still passes the “reviewed” manifest.

Store a reviewed cryptographic digest for each migration file, hash each corresponding file at readiness time, and bind the same digest to the applied record. Test content changes, marker-only comments, and markers moved to the wrong file.

## Secret scanner has an exempt tree and common format gaps

**[medium, confirmed]** repository scanning excludes the entire `tests/fixtures/policy/stage7` tree, then re-injects selected directories only in tests that already expect failure. A real secret added there cannot fail the normal policy, and extra leaks in an existing negative directory are masked by its known failure. The allowlist also skips common secret-bearing formats such as `.envrc`, `.pfx`, `.jks`, `.tfvars`, `.toml`, `.ini`, and `.properties` (`scripts/check-stage7-policy.mjs`, lines 79–94).

Replace the directory exemption with an exact allowlist of reviewed synthetic fixtures and expected hashes or sentinel content, scan every other file, and classify additional environment/key-store/config formats. Add clean near-match fixtures so broader signatures do not make documentation and placeholders unmanageable.

## Verification results leave the database blocker unexecuted locally

Targeted checks passed TypeScript typechecking, the Stage 7 policy, `git diff --check`, eight Stage 7 unit tests, and nine deterministic integration tests for acceptance, provider readiness, and rollback. **[high, confirmed]** the live PostgreSQL suite was not executable here without `TEST_DATABASE_URL`; its setup failure follows directly from the repeated fixture IDs and global uniqueness constraint above.
