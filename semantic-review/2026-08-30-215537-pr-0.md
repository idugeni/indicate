## Previous-host authority is proven before cleanup work is persisted

`DomainProvisioningService.activate` applies malformed-host and reserved-control-host rejection to both the target and previous hostname before calling the repository (`src/application/stage5/domain-provisioning-service.ts:26-31`). `DrizzleStage5Repository.beginActivation` then locks the target Site and invokes `indicate_private.is_stage5_previous_host_owned` before changing Site state or inserting an activation attempt (`src/infrastructure/db/repositories/drizzle-stage5-repository.ts:90-115`). This ordering prevents an untrusted previous hostname from reaching the durable attempt and its eventual invalidation plan.

The proof requires an activation-history row for the same Organization, Site, and hostname, then rejects the value if any different Site currently maps it (`drizzle/0008_stage5_production_boundaries.sql:66-88`). The SECURITY DEFINER boundary lets the conflict check see cross-tenant rows hidden from the caller by forced RLS, while exposing only a boolean and granting the runtime role only EXECUTE permission. The in-memory repository applies the same history-and-conflict rule.
