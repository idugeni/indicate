# Stage 5 remediation with recovery and cache-consistency gaps

The remediation closes 14 of the prior review’s 18 findings, including runtime-role public discovery, Region eligibility, pending-host proof, provider verification, fenced invalidation acknowledgement, cache-aware serving, verified public claims, and hostname-correct metadata. The mandatory quality gate and fresh PostgreSQL contract are materially stronger than the prior pass. Production activation reconciliation still cannot consume claimed database rows, and cache invalidation does not become authoritative when a mutation commits. New API-boundary regressions also misstate whether work was persisted and expose the internal reconciler on every valid host.

Watch for: **[critical · confirmed]** claimed activation rows crash during production mapping; **[high · confirmed]** pending or overlapping invalidations can serve stale content; **[high · confirmed]** new verified affiliations do not invalidate public claims; **[medium · confirmed]** Stage 5 operational endpoints have misleading and over-broad failure/exposure behavior.

**Verdict**: NEEDS_CHANGES

## High-level view

The RLS-safe discovery function and tenant-scoped content transaction close the original public-runtime blocker, including active Region enforcement and verified affiliation scope. Provider operations now require public DNS delegation and explicit Vercel verification, partition purges by zone, and persist activation/deactivation phases for retry.

**[critical · confirmed]** That persisted domain saga is not operational through the production repository. The activation claim function returns PostgreSQL snake_case columns, while the repository maps them as Drizzle camelCase rows; the first due attempt fails before resumption.

**[high · confirmed]** Public reads now use Hostname Context cache identities and consult PostgreSQL bypass state, but writes only turn bypass on after dispatch failure. Any one successful task also turns it off without considering other unresolved tasks for the Site, leaving stale-serving windows around queued and overlapping mutations.

**[high · confirmed]** Mutation transactions create broader invalidation plans for public surfaces, but creating an already-verified affiliation is skipped. Existing public articles can retain an obsolete official-claim projection.

**[medium · confirmed]** Invalid configuration and missing resources are reported as durably queued even when no attempt exists. The reconciler’s proxy exemption also makes the internal path reachable through every valid public hostname and allocates runtime resources before rejecting an unauthenticated request.

## Persisted activation recovery breaks at the SQL row boundary

**[critical · confirmed]** `claimActivationAttempts` executes `SELECT * FROM indicate_private.claim_stage5_activation_attempts(...)` and passes the raw PostgreSQL result to `mapAttempt` (`src/infrastructure/db/repositories/drizzle-stage5-repository.ts:134-136`). PostgreSQL labels the returned fields `organization_id`, `next_attempt_at`, and `reconciliation_claim_token`, while `mapAttempt` reads `organizationId`, `nextAttemptAt`, and `reconciliationClaimToken` (`src/infrastructure/db/repositories/drizzle-stage5-repository.ts:108-110`). `iso(row.nextAttemptAt)` receives `undefined` and throws before `DomainProvisioningService.reconcile` can resume activation or deactivation. Alias the result or map snake_case explicitly, then run both operations through `DrizzleStage5Repository` as `indicate_runtime`.

## Durable bypass starts too late and ends too early

**[high · confirmed]** mutation and activation transactions insert `invalidation_tasks`, but no enqueue path enables `cache_bypasses`. The only transitions are `bypass = true` after `fail_stage5_invalidation` and `bypass = false` after completion (`drizzle/0008_stage5_production_boundaries.sql:117-121,152-156`). A committed mutation can continue reading its previous `unstable_cache` entry until dispatch. Enable bypass in the transaction that creates each task.

**[high · confirmed]** `complete_stage5_invalidation` unconditionally sets Site bypass false when one task completes (`drizzle/0008_stage5_production_boundaries.sql:117-121`). Another task may already be pending, processing, failed, or inserted while the first is in flight, so that completion can re-enable stale reads. Clear bypass under a Site-scoped lock only when no unresolved invalidation remains; terminal failures must keep it enabled.

## Verified affiliation creation skips affected public Sites

**[high · confirmed]** Stage 3 creates affiliations active and verified in one mutation (`src/application/stage3/tenant-business-service.ts:331-337`), immediately changing `officialInstitution` for existing published articles. The invalidation collector continues when the affiliation has no prior row (`src/infrastructure/db/repositories/drizzle-stage3-repository.ts:228`), so `affiliation.create` emits no Site, article, SEO, or feed invalidation. Treat insertion as a public projection change and test an already-published verified publisher.

## Stage 5 operational routes blur trust and persistence boundaries

**[medium · confirmed]** the CMS command catches every provisioning exception and returns `DEPENDENCY_UNAVAILABLE` with “durably pending and will be retried” (`app/api/cms/stage5/route.ts:31-32`). Reserved-host rejection occurs before `beginActivation`, and nonexistent Sites or invalid deactivations can fail before insertion. Return validation/conflict/resource outcomes separately and reserve this response for committed attempts.

**[medium · confirmed]** middleware exempts `/api/internal/stage5/reconcile` before control/public host classification (`proxy.ts:17-18`), making the internal operation reachable through every valid public host. The route builds the database/provider composition before checking its Bearer secret (`app/api/internal/stage5/reconcile/route.ts:11-16`). Keep constant-time comparison, but bind the route to an operational host or platform scheduler and reject unauthorized calls before allocation.

## Passing gates omit the failing production paths

**[high · confirmed]** the PostgreSQL suite exercises discovery, content loading, pending proof, and invalidation fencing, but never calls `claimActivationAttempts`; recovery tests use the camelCase in-memory repository. Cache tests begin bypass only after forced dispatch failure, and no test spans task creation through all outstanding tasks. Stage 3 tests create affiliations without asserting production invalidation. Add these contracts to the mandatory runtime-role/integration gate; prior finding 18 remains incomplete.
