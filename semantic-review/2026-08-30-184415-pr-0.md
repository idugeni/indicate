# Stage 3 verified User context, public eligibility, and historical analytics

Major Stage 3 now derives Supabase Auth identity at the server boundary, establishes narrow User-RLS context, makes Official Affiliation ownership immutable on update, follows immutable job targets, gates public content on active Sites/Regions, and derives Membership display names from persisted Users. Five prior findings are closed, and the immutable-target half of the analytics finding is closed; non-published outcome dates still use a general record-update timestamp. A fresh route review also found that the production CMS cannot discover a User's organizations because its initial Membership query has no tenant context. **Watch for:** **High, confirmed** the production organization selector is empty under forced tenant RLS; **High, confirmed** failed/queued/retrying outcomes can move between date ranges after a non-state assignment edit; **Medium, confirmed operational risk** the 14 PostgreSQL and one Supabase provider tests have no observed green result.

**Review decision**: CHANGES_REQUESTED

**Verdict**: NEEDS_CHANGES

## High-level view

Verified Auth identity flows from Supabase `getUser()` into a transaction-local definer function that validates the Auth UUID against the local actor before setting User RLS context. Membership reads, updates, display projection, and denied-User attribution now share that verified context without relaxing forced RLS or public grants.

Affiliation ownership is immutable at the strict command boundary, job analytics follows persisted targets and job transition dates, and public selection requires active Site lifecycle, completed activation, active Region, and an active published assignment. Article-Site analytics still dates every non-published outcome by `updatedAt`, which assignment reactivation changes without a publication-state transition.

The production CMS shell queries Memberships to discover organizations before any Organization context exists. Forced tenant RLS therefore hides every organization, while E2E uses fixture organizations and misses the failure.

Generated properties now use multi-tenant and invalid-state reference models, and the fresh reruns passed all 11 property tests plus 24 deterministic integrations. PostgreSQL execution is mandatory in CI, but no provider-backed result is available, so checkpoint evidence remains operationally incomplete.

## Forced tenant RLS hides the production organization selector

After `verifyCookieSession()` and local User resolution, `app/cms/page.tsx:39` calls `listActiveOrganizationsForUser`. That method directly joins `memberships`, `organizations`, and `roles` without setting `app.organization_id` (`drizzle-authorization-repository.ts:26-32`). Memberships are in the forced tenant-policy set, and Organizations use the same `current_organization_id()` boundary (`0001_stage2_security.sql:167-180,187-191`).

**High, confirmed:** the runtime role receives an empty organization list on the real `/cms` page. Stage 3 APIs can authorize a caller who already supplies an Organization ID, but the UI cannot discover or select it; browser tests substitute hardcoded `E2E_ORGANIZATIONS` (`app/cms/page.tsx:14-26`). Add a narrowly scoped `SECURITY DEFINER` projection bound to server-verified Auth identity, revoke public execution, grant only the runtime role, and exercise this production path in the live PostgreSQL contract.

## Article-Site outcome dates are not state-transition dates

Job dimensions now correctly traverse `publishing_job_targets.article_site_id`, and jobs are filtered by `finalized_at ?? updated_at`. Article-Site outcomes instead use `publishedAt ?? updatedAt` (`policies.ts:107-126`). Published outcomes have a dedicated timestamp, but queued, processing, retrying, and failed outcomes do not.

**High, confirmed:** reassigning an existing Article-Site sets `active`, increments version, and rewrites `updatedAt` without changing its publication state (`tenant-business-service.ts:447-449`). A failed outcome can therefore move into a later analytics range merely because its assignment was reactivated. Add an `outcome_at`/`state_occurred_at` field updated only with publication-state transitions, use it for outcome filtering, and make Property 9 generate a state transition followed by a later non-state assignment mutation.

## Verified context, immutable ownership, public gating, and generated evidence

The route obtains `verifiedAuthUserId` from Supabase `getUser()`, not request input. `set_verified_user_context` validates that Auth UUID against the local actor before setting `app.auth_user_id`; the display-name projection requires the verified caller to hold an active Membership in the current Organization. Public execution is revoked and only the runtime role receives execute access (`0004_stage3_verified_user_context.sql:4-74`). The PostgreSQL contract covers Membership listing/update and denied-User audit attribution.

Affiliation updates reject `publisherId` and `siteId`, retain ownership from the stored record, and persist only mutable fields. Public selection requires active Site lifecycle and activation state, active Article Region, and an active published Article-Site relation (`policies.ts:45-56`). Membership commands reject caller-supplied display names and resolve persisted User data (`tenant-business-service.ts:246-252`). Explicit Organization predicates, composite same-Organization keys, one canonical Article row, non-disclosing denials, RBAC, transactional redacted audits, server-only configuration, and the one-resource topology remain intact in the reviewed paths.

Property 9 now generates foreign tenants, Sites/Regions, immutable targets, states, and dates against a reference model, but assigns each outcome's `updatedAt` directly and does not model later non-state edits. Properties 11–13 and 34 materially cover canonical round trips, invalid assignment atomicity, activation/Region/filter eligibility, and attributable immutable/redacted/atomic audits. The fresh property run passed 11/11 at 100 cases each.

## Provider execution remains a checkpoint condition

The fresh integration run passed 24 deterministic tests and skipped 14 PostgreSQL plus one Supabase Auth contract. The workflow provisions PostgreSQL and unconditionally runs `npm run test:postgres:live`, closing the prior CI-wiring gap.

**Medium, confirmed operational risk:** no result from that CI job is observed, and the Supabase contract still needs a credentialed environment. This is separate from the two code defects. Tasks 7.1–7.16 cannot be marked complete until organization discovery and outcome dating are fixed with corresponding contracts. Checkpoint 8 must additionally wait for the complete local gate and mandatory PostgreSQL CI job to be observed green under the approved local/CI model.
