# Concurrent Telegram coherence serialized but not deployable

The final remediation makes active Telegram mapping writes lock the same Membership row used by Membership Role changes, closing the previously reported write-skew interleaving in the SQL itself. A production-adapter PostgreSQL regression now proves the Role-change session waits for an open mapping transaction and finishes with no active inconsistent mappings. The complete local Stage 2 gate passes with 34 unit, 5 property, 15 deterministic integration, a secure production build, and 7 Playwright tests; the 11 PostgreSQL cases remain skipped locally and mandatory in the PostgreSQL 17 CI job. Checkpoint 6 is still blocked because the production Drizzle migration path does not discover migration `0003`, so deployed databases do not receive the locking guard. **Watch for:** **confirmed** `drizzle/meta/_journal.json` ends at migration `0002`, while `scripts/migrate.ts` uses Drizzle's journal-driven migrator; `0003_stage2_authorization_hardening.sql` is omitted from `db:migrate` even though tests execute it manually.

**Verdict**: NEEDS_CHANGES

## High-level view

The reciprocal locking design now serializes both mutation directions on one Membership row. If a mapping write wins, the Role change waits and deactivates that committed mapping; if the Role change wins, mapping activation wakes against the new Membership Role and fails coherence validation.

The live regression exercises `AuthorizationService.changeMembershipRole`, observes its runtime connection waiting through `pg_stat_activity`, commits the competing mapping, and verifies the Role update plus zero active mismatches. Migration-source coverage also requires `FOR UPDATE`.

**Confirmed:** the release path differs from the tested path. Live tests hard-code `0003` in their migration list, while Drizzle's production migrator reads only tags in `drizzle/meta/_journal.json`; the missing journal entry leaves deployed schema version 3 and the old non-locking function in place.
