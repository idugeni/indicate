# Stage 6 external-entrypoint hardening and replay recovery

The follow-up separates platform authority from tenant roles, fences replay workers with rotating claim tokens, captures Telegram business receipts in the mutation transaction, and closes the route/source and pre-authentication rate-limit gaps. The eight original findings and four prior follow-up concerns are addressed in the production paths and adversarial coverage reviewed here. One release-gate defect remains: the fresh PostgreSQL bootstrap does not apply the hardening migration required by the Stage 6 contract. **Watch for: Medium, confirmed — the combined PostgreSQL contract initializes only through migration 0009, so migration 0010 and its runtime-role defenses are never reached on a fresh database.**

**Verdict**: NEEDS_CHANGES

## High-level view

Tenant role schemas now admit only organization-scoped Stage 6 permissions, while platform customer administration is provisioned through a runtime-inaccessible grant table and revalidated against the verified transaction-local user. Exact control-plane hosts, Cloudflare origin proof, and a trusted-source bucket before API-key lookup close the original network and unauthenticated-work boundaries; Stage 6 denial paths now write sanitized best-effort audits.

Telegram takes the replay claim before identity lookup, rotates a UUID fence on lease reclaim, requires that fence for bind/prepare/finalize, and uses an audit trigger to reject stale business writes while recording terminal receipts atomically. Prepared and rejected outcomes are replayable without rerunning shared services, and the generic webhook has a deterministic validation outcome rather than an arbitrary mutation callback.

The in-memory, property, build, and browser gates pass with the new adversarial cases. **Medium, confirmed:** the fresh PostgreSQL bootstrap still ends at migration 0009 even though the Stage 6 live suite requires version 11, leaving the hardening SQL unexecuted by the combined command and blocked from validation in this sandbox.

## Fresh PostgreSQL bootstrap omits the security-hardening migration

**Medium, confirmed.** `npm run test:postgres:live` runs the Stage 2 PostgreSQL suite first and the Stage 6 suite last (`package.json:32-39`). The Stage 2 suite iterates its `migrationFiles` list and executes every statement on the fresh database (`tests/integration/stage2-postgres-live.integration.test.ts:112-117`), but that list stops at `drizzle/0009_stage6_external_entrypoints.sql` (`tests/integration/stage2-postgres-live.integration.test.ts:21`). Migration 0010 registers schema version 11 (`drizzle/0010_stage6_security_hardening.sql:365-366`), and the Stage 6 suite requires that version before setup (`tests/integration/stage6-postgres-live.integration.test.ts:37-40`). The combined command therefore reaches Stage 6 with only version 10 and fails before exercising platform impersonation, replay fencing, stale-write rejection, or receipt capture. Add migration 0010 to the bootstrap list and rerun the complete fresh PostgreSQL command.

The non-PostgreSQL gate passed in this review: 62 unit tests, 34 property tests, 60 integration tests with 39 environment-dependent skips, the secure production build, and 25 Playwright tests. `npm audit --omit=dev` reported zero vulnerabilities and `git diff --check HEAD` passed. A fresh PostgreSQL 17 container started, but the host could not connect to its published loopback port (`EHOSTUNREACH 127.0.0.1:34691`); the temporary container was removed after the failed attempt. Migration 0010 was reviewed manually, but its syntax and runtime behavior remain unexecuted here.
