# Stage 5 remediation with durable recovery and cache-safe public delivery

The change addresses the original 18 findings and the seven follow-up defects across runtime-role discovery, provider recovery, cache invalidation, public claims, operational routing, and mandatory PostgreSQL coverage. Activation/deactivation claims now map through the runtime repository, invalidation bypass spans enqueue through the last outstanding task, verified affiliation creation reaches affected Sites, and reconciliation is authorized on the CMS control-plane host. One newly exposed trust-boundary gap remains: **[high · confirmed]** the activation API accepts an arbitrary previous hostname and later uses it for Cloudflare purges without proving that hostname belongs to the Site or tenant.

Watch for: **[high · confirmed]** a tenant user with `sites.manage` can make a successful activation enqueue purges for another tenant’s or a reserved control-plane hostname through the unvalidated `previousHostname` field.

**Verdict**: NEEDS_CHANGES

## High-level view

Public discovery now uses the narrow security-definer lookup and tenant-scoped reads. Activation and invalidation claims retain their fences through the runtime repository, provider failures remain durable, and PostgreSQL bypass begins atomically at task insertion and clears only after all Site work completes.

Mutation-driven invalidation covers settings, publication, media, publisher, and verified affiliation changes. Public rendering enforces active Regions, verified claim scopes, hostname-correct assets, branded failures, and embedded cache context; CI separately runs the runtime-role contracts against PostgreSQL 17.

**[high · confirmed]** The old-host cleanup path still crosses the tenant/provider boundary without an ownership check. `previousHostname` comes directly from the CMS request, is normalized but not checked against the Site’s persisted transition or the reserved-host set, and is persisted for later Cloudflare URL and hostname purges.

## Request-controlled previous hostname reaches Cloudflare purge authority

**[high · confirmed]** `app/api/cms/stage5/route.ts:15,33` accepts `previousHostname` from the request body and passes it to `DomainProvisioningService.activate`. The service normalizes that value, but its reserved-host check applies only to `rawHostname` (`src/application/stage5/domain-provisioning-service.ts:27-31`). `DrizzleStage5Repository.beginActivation` verifies that the current hostname matches the target Site but stores `previousHostname` without verifying its ownership (`src/infrastructure/db/repositories/drizzle-stage5-repository.ts:90-107`).

That persisted value enters the completion invalidation plan. `InvalidationDispatcher` sends every plan URL to `purgeExactUrls` and calls `purgeHostname` for both current and previous hosts (`src/application/stage5/invalidation.ts:32-34`); the Cloudflare adapter checks zone membership, not Organization ownership. A user authorized to manage one Site can therefore submit another tenant’s hostname—or a reserved control-plane hostname under the same managed zone—and flush its CDN cache when activation completes or terminal recovery runs.

Derive the previous hostname from a server-side, tenant-scoped Site/domain transition record. If the API must carry it for optimistic concurrency, compare it under the Site lock to persisted history, reject reserved/control-plane values, and add a contract proving unauthorized values cannot enter an invalidation task. The otherwise passing Stage 5 gate has no ownership test for this field.
