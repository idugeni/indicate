# Stage 6 external entry points, credentials, and platform administration

This change adds Telegram publishing workflows, scoped API credentials, webhook replay protection, Redis rate limiting, and platform customer/subscription administration on top of the existing tenant services. Article, Media, and Publication behavior is shared across CMS, API, and Telegram, while credential-state changes and success audits use database transactions. The release is not ready because tenant role management can mint platform-wide authority and the new replay and request boundaries have security and recoverability gaps. **Watch for: critical — confirmed tenant-to-platform privilege escalation; high — confirmed replay claims stranded after committed work; high — confirmed spoofable webhook source identities on alternate hosts; high — confirmed unbounded API-key authentication attempts; medium — confirmed missing denial audits and incomplete Telegram failure delivery/replay.**

**Verdict**: NEEDS_CHANGES

## High-level view

The new Stage 6 permissions are fed into ordinary tenant role creation, including `platform.customer.admin`. **Critical, confirmed:** a user with tenant `role.manage` can assign that global permission to a role, attach it to a membership, and satisfy both application and database platform checks.

Replay claims prevent concurrent duplicate execution in the success path, but completion happens after the business handler commits. **High, confirmed:** completion failure leaves the claim in `claimed`, so the original request reports failure and every retry reports “already processing” without recovering the persisted outcome. **Medium, confirmed:** Telegram also resolves tenant identity before taking the replay claim, contrary to the required trust-boundary order.

The new routes inherit broad hostname proxy rules. **High, confirmed:** API and webhook routes remain reachable through wrong control-plane and arbitrary production hosts, allowing direct callers to provide `cf-connecting-ip` and partition around webhook limits. **High, confirmed:** API-key authentication, including scrypt verification for known lookup IDs, runs before any limiter.

**Medium, confirmed:** Stage 6 authorization denials bypass the implemented denial-audit method. **Medium, confirmed:** Telegram validation failures return HTTP errors without sending concise guidance to the chat, and duplicate rejected updates do not reproduce the original outcome.

<summary>Issues (8)</summary>

1. **Critical — tenant-to-platform privilege escalation (confirmed)** — Tenant role commands can grant `platform.customer.admin`, which unlocks every Customer Organization. Exclude platform permissions from tenant role management and add a separately authorized provisioning path.
2. **High — stranded replay claims after committed work (confirmed)** — Business mutations commit before replay completion, so a completion failure leaves a permanent `claimed` row and no retrievable outcome. Make outcome persistence atomic with the mutation or add a durable lease/outbox reconciliation path.
3. **Medium — Telegram replay claim ordering (confirmed)** — Telegram identity is resolved before the source/update replay claim. Claim the authenticated update before tenant mapping, then bind the resolved Organization safely.
4. **High — spoofable webhook source identity (confirmed)** — New webhook routes are reachable on alternate production hosts where callers can supply `cf-connecting-ip` and evade source limits. Enforce exact route hostnames and trust source headers only on a guaranteed Cloudflare path.
5. **High — unlimited API-key authentication work (confirmed)** — Invalid credentials reach lookup and potentially scrypt before rate limiting. Add a trusted-source pre-authentication limit and retain the current actor/key limit after authentication.
6. **Medium — missing Stage 6 denial audits (confirmed)** — API-key, customer/subscription, and Telegram-mapping denials never call `recordDenial`. Route authorization failures through a sanitized best-effort audit helper.
7. **Medium — Telegram failure delivery and replay mismatch (confirmed)** — Invalid workflow input is neither sent to the chat nor replayed consistently for duplicate updates. Persist and send a sanitized failure reply, then return that same rejected outcome on duplicates.
8. **Medium — adversarial coverage gaps (confirmed)** — Tests omit escalation, replay-completion failure, direct-host spoofing, pre-auth limits, denial audits, and rejected Telegram replay. Add service, runtime-role, route, and E2E cases for these boundaries.

<details><summary>Details</summary>

## Tenant role management can mint platform administrators

**Critical, confirmed.** `isStage3Permission` now admits every Stage 6 permission, including `platform.customer.admin` (`src/domain/stage3/permissions.ts:14-15`, `src/domain/stage6/permissions.ts:1-9`). Role persistence loads tenant permissions together with rows whose `organization_id` is null, then writes whichever names the role command selected (`src/infrastructure/db/repositories/drizzle-stage3-repository.ts:160-165`). There is no separate platform-authority check around that selection.

`CustomerService` treats presence of the permission in `actor.permissionSet` as platform authority (`src/application/stage6/customer-service.ts:12`), and `stage6_has_platform_permission` accepts any active membership whose role links to the platform permission (`drizzle/0009_stage6_external_entrypoints.sql:177-193`). A tenant role manager can therefore create or update a role with `platform.customer.admin`, assign it to a membership, and gain list/create/update access across all Customer Organizations and subscriptions. Exclude platform-scoped names from tenant role schemas and repository selection, then provide a separately protected provisioning path for genuine platform administrators.

## Replay completion can strand committed mutations

**High, confirmed.** Telegram executes the shared service and only then invokes `completeReplay` (`src/application/stage6/telegram-workflow-service.ts:75-79`); the generic service likewise awaits the handler before completion (`src/application/stage6/webhook-service.ts:57-61`). These are independent operations, while Article, Media, and Publication mutations commit in their own transactions.

If terminal replay persistence fails after the handler commits, the request returns a dependency failure and the replay row remains `claimed`. Later deliveries return a permanent conflict (`src/application/stage6/telegram-workflow-service.ts:66-73`, `src/application/stage6/webhook-service.ts:43-52`); the SQL finisher only transitions `claimed` rows and there is no lease, recovery command, or completion retry (`drizzle/0009_stage6_external_entrypoints.sql:151-173`). Callers cannot recover the committed outcome or distinguish it from unprocessed work. Persist an outcome reference in the tenant mutation transaction where possible, or add a durable processing lease/outbox and reconciliation path that finishes a stranded claim without re-running the mutation.

**Medium, confirmed.** Telegram resolves `TelegramIdentity` before calling `claimReplay` (`src/application/stage6/telegram-workflow-service.ts:60-65`), although the Stage 6 design requires secret, freshness, and replay validation before mapping identity. Claim the source/update first, then bind the resolved Organization without allowing another tenant to adopt the same source/update ID.

## Alternate hosts make webhook source limits spoofable

**High, confirmed.** The CMS host allows nearly every path, the API host allows most `/api/*` paths, and unknown production hosts block only CMS/internal/health paths before falling through (`proxy.ts:21-44`). The new `/api/webhooks/*` routes can therefore run on CMS, API, and arbitrary production authorities, while `/api/v1/commands` can run outside the configured API hostname.

Both webhook routes treat request-supplied `cf-connecting-ip` as the validated source (`app/api/webhooks/generic/route.ts:14-18`, `app/api/webhooks/telegram/route.ts:13-18`). A direct request through a non-Cloudflare Vercel authority can set a new syntactically valid value per request and receive a fresh Redis bucket. Restrict each route family to its exact configured hostname, reject default authorities, and derive source identity only from infrastructure guaranteed to overwrite the header.

## API-key verification is outside the rate-limit boundary

**High, confirmed.** `/api/v1/commands` calls `ApiKeyService.authenticate` before consuming a rate-limit bucket; only successful authentication receives the Organization/key-partitioned limit (`app/api/v1/commands/route.ts:18-25`). Invalid, revoked, expired, and wrong-secret attempts are unlimited. A known lookup ID forces slow scrypt derivation on every attempt, creating an unauthenticated CPU-exhaustion and credential-guessing surface.

Apply a trusted-source pre-authentication limit before lookup/hash work, then retain the current Organization/key limit after successful authentication. The pre-auth identity needs the same exact-host protection as the webhook boundary.

## Stage 6 authorization denials bypass security auditing

**Medium, confirmed.** `DrizzleStage6Repository` implements `recordDenial` (`src/infrastructure/db/repositories/drizzle-stage6-repository.ts:148`), but API-key, customer/subscription, and Telegram-mapping services return `this.denied(actor)` directly on permission and cross-tenant failures (`src/application/stage6/api-key-service.ts:77-87,106-113`, `src/application/stage6/customer-service.ts:16-43`, `src/application/stage6/telegram-mapping-service.ts:19-31`). Those events are non-disclosing externally but absent from the required security audit trail. Route Stage 6 authorization failures through an async helper that attempts a sanitized action/target audit while preserving the same external denial if audit persistence fails.

## Telegram failures are neither delivered nor replayed as the same outcome

**Medium, confirmed.** Successful results call `telegram.send`, but failed shared-service or validation results are stored only as `{ code }` and returned from the HTTP handler (`src/application/stage6/telegram-workflow-service.ts:75-79`). Invalid Site selection, for example, constructs concise field guidance but exits through that unsent path (`src/application/stage6/telegram-workflow-service.ts:139-143`). The user receives no corrective chat message.

The duplicate branch handles only `processed` outcomes and treats `rejected` as “already processing” (`src/application/stage6/telegram-workflow-service.ts:66-73`). Persist a sanitized reply with the failure code, send it to the mapped chat, and return the same rejected logical outcome on duplicate delivery without invoking business services again.

## Adversarial Stage 6 paths remain untested

**Medium, confirmed.** **Not tested:** tenant `role.manage` granting `platform.customer.admin`; completion failure after a committed handler; stranded-claim recovery; rejected Telegram duplicate behavior and chat delivery; direct/default-host access with caller-supplied `cf-connecting-ip`; pre-authentication API rate limiting; and denial-audit persistence. Add these at service, PostgreSQL runtime-role, route, and E2E levels. The live PostgreSQL suite inserts the platform permission into a tenant role as setup (`tests/integration/stage6-postgres-live.integration.test.ts:42-50`), masking the escalation instead of asserting that tenant role management cannot create the binding.
