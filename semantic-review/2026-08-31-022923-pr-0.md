# Stage 7 full-file migration integrity and production-readiness release gate

The fixes replace prefix-only migration hashing with full-file SHA-256 canonicalization and align the production runbook with the schema-14, 14-migration release contract. Readiness now validates those local digests, compares the complete applied manifest, and requires both R2 management-plane privacy and an S3 `HeadBucket` data-plane probe. The previous eight findings remain closed across evidence cleanup, fixture identity, evidence parsing, migrated persistence, R2 credentials, Telegram throttling, migration integrity, and secret scanning. **Watch for:** **[medium, confirmed]** the Stage 7 live PostgreSQL test still expects the obsolete schema-14 checksum, so the CI job that provisions PostgreSQL 17 will fail after applying the current migration.

**Verdict**: NEEDS_CHANGES

## High-level view

Migration canonicalization normalizes CRLF to LF, parses one required registration statement, replaces only the checksum literal for the exact version/name self-row, and hashes the entire remaining file. Migration 0000 has no self-registration and is hashed without substitution; malformed, missing, duplicate, or unexpected core registrations fail closed.

The readiness adapter recomputes all 14 local file digests against the ordered journal and reviewed manifest, then requires the runtime database to expose the same 14 version/name/checksum records. The runbook consistently describes schema 14 and separates Cloudflare management-plane bucket/privacy inspection from the production R2 S3 credential probe.

Evidence deletion remains confined to known files below `.stage7-evidence`; region IDs remain globally unique; promotion evidence remains exact and internally consistent; and the migrated PostgreSQL acceptance journey still exercises runtime-role discovery, Drizzle publication/public reads, cache isolation, and credential denial. The Telegram challenge retains dedicated one-request capacity, and the scanner retains content-bound allowances rather than exempting its fixture tree.

The normal Stage 7 gate skips database suites without `TEST_DATABASE_URL`, but CI supplies it and runs this assertion after migration 0013 has inserted the current value.

## Full-file canonicalization binds all 14 reviewed migrations

Independent mutation checks confirmed that every current migration computes to its `REVIEWED_MIGRATION_MANIFEST` checksum and that migration 0013 contains the matching version/name/checksum tuple for all 14 records. Converting each file from LF to CRLF leaves its digest unchanged. Appending executable SQL after the registration changes the digest, as does changing a non-self checksum in the multi-row registration or historical digest list; changing only the exact matching self-checksum literal leaves the digest stable.

The parser skips quoted/commented SQL while locating registration statements, requires one structurally valid `INSERT INTO [public.]indicate_schema_migrations`, and requires exactly one row matching the migration version and name. Removing the registration, duplicating it, or changing its expected column structure throws instead of producing a reviewable checksum. Migration 0000 rejects an unexpected registration and hashes every normalized byte, including appended content.

`ProductionReadinessAdapter.migrationManifest()` reads the ordered journal, requires exactly 14 entries with matching indices/tags, hashes each corresponding SQL file through this canonicalizer, and returns an invalid manifest on any read, parse, or digest failure. Its database probe reads the first 14 applied rows in version order and `matchesReviewedMigrationManifest()` requires exact length, order, version, name, and checksum equality; schema version 14 or newer alone cannot bypass the applied-manifest check.

Update the assertion to the current reviewed value, preferably sourcing the expected schema-14 record from `REVIEWED_MIGRATION_MANIFEST` so the cryptographic unit test remains the single file-to-digest authority.

The runbook names version 14, the 14-entry sequence through `0013_stage7_migration_body_digests`, full migration-body hashing including trailing SQL, and the exact readiness behavior. No schema-13 instruction remains.
