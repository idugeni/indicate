The Stage 7 PostgreSQL fixture now generates the 16-character API-key lookup ID required by the production credential parser, closing the authentication failure from CI run 33351300233. The prior fixture generated a 17-character lookup ID that the fail-closed production parser rejected before repository lookup. Reducing the ordinal padding by one yields exactly 16 characters for all three configured roots while preserving deterministic uniqueness.

The database-backed journey remains the end-to-end parser contract because authentication must succeed before its nine publication scenarios execute.

Only the live test fixture changes. Production malformed-credential denial, hashing, active/expiry and scope checks, actor derivation from the stored key, tenant isolation, and forced-RLS behavior remain untouched.

## Fixture correction reaches the failed authentication boundary

CI run 33351300233 passed the quality-gate job but failed the PostgreSQL job at the first `authenticated.ok` assertion in the nine-scenario journey. The old lookup was six literal characters plus eleven padded digits; production `parseCredential` accepts exactly 16 lookup characters, so authentication returned its non-disclosing denial before querying Stage 6 storage.

The corrected lookup is six literal characters plus ten padded digits for root ordinals 1–3. The same `liveCredential` output supplies the inserted `api_keys.lookup_id`, authentication plaintext, hashed secret, and salt, so a successful parse reaches the matching organization row without changing production behavior.

## Always-on coverage guards the database-gated seam

The new test uses ordinary `describe` rather than the `TEST_DATABASE_URL`-gated suite. `npm run test:postgres:stage7` without PostgreSQL executed it successfully while skipping the four live contracts, proving the regression assertion is always discovered.

The assertion derives credentials from the actual readiness fixture instead of hand-selecting ordinals. It fails for the original 17-character lookup, malformed prefix or separator, invalid base64url characters, wrong component lengths, or duplicate configured-root credentials. Its local pattern mirrors the current private parser contract; the live journey independently exercises `ApiKeyService.authenticate` when PostgreSQL is available.

## Production and tenant trust boundaries are unchanged

The diff contains no production changes. `parseCredential` remains anchored to the exact 16/43 format, parse failures remain non-disclosing, stored hash and lifecycle checks remain mandatory, and organization identity and scopes continue to come from the stored key rather than credential text.

The existing live journey still creates one credential per organization, publishes through the authenticated stored-row actor, compares own and foreign job visibility, rejects foreign cache content, and exercises forced-RLS exact-host discovery. This fix only allows those checks to proceed past credential parsing.
