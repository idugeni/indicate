# Stage 2 tenant isolation follow-up

The follow-up adds production Supabase identity linkage, server-authorized Active Organization switching, a dedicated RLS-bound runtime login, transaction-bound authorization revalidation and Membership mutation, mandatory production schema gating, stronger Publisher actor constraints, and opt-in PostgreSQL coverage. The deterministic Stage 2 gate passes: 31 unit, 5 property, and 15 integration tests, a secure production build, and 7 Playwright tests; three live hooks remain skipped without external credentials. The prior redirect, deployable test bypass, non-user claim trust, runtime-role, migration-metadata, schema-gate, and basic PostgreSQL-coverage findings are materially addressed. **Watch for:** **confirmed** inactive local Users can still enter the live CMS when their Membership remains active, **confirmed** the shared runtime role can mutate platform-scoped Permissions, **confirmed** missing Membership/Role targets do not produce the required denial and can create false success audits, and **confirmed** the live PostgreSQL suite still omits required transaction/concurrency paths.

**Verdict**: NEEDS_CHANGES

## High-level view

The live CMS verifies Supabase Auth and links the identity locally before resolving Membership. **Confirmed:** both production entry points bypass the existing status-aware identity resolver and continue with an `inactive` or `archived` local User when that User still has an active Membership and Role.

The dedicated `indicate_runtime` login makes forced RLS effective and migration metadata is read-only. **Confirmed:** its blanket table DML grant combines with the `permissions` policy's unconditional `scope = 'platform'` branch, allowing any runtime tenant context to insert, update, or delete the shared platform permission catalog.

Membership role changes now place permission revalidation, mutation, and audit in one transaction. **Confirmed:** a zero-row Membership update returns `ok: true` and appends a `succeeded` audit, while an absent or cross-Organization Role reaches a foreign-key error instead of the non-disclosing denial used by other authorization misses.

The opt-in PostgreSQL suite applies all migrations and verifies runtime-role RLS, append-only audit deletion defense, and one composite tenant relation. **Confirmed:** it does not execute the production transaction manager or seed repository and omits audit-failure rollback, Membership revocation concurrency, unique-relation conflicts, identity-link concurrency, Publisher actor constraints, and seed rerun/rollback against PostgreSQL.

<details><summary>Details</summary>

## Local User deactivation is bypassed by live CMS adapters

`resolveAuthenticatedUser` rejects a linked User unless `status === 'active'` (`src/application/auth/resolve-authenticated-user.ts:18-22`). The CMS page and Active Organization endpoint instead call `linkLocalUser` directly and proceed to `findActiveMembership` without inspecting status (`app/cms/page.tsx:55-63`, `app/api/cms/active-organization/route.ts:49-56`). **Confirmed:** an `inactive` or `archived` local User with a still-active Membership can load the protected CMS and set the Active Organization. Route both adapters through the status-aware resolver, or reject any non-active local identity before the first Organization lookup.

## Runtime RLS permits tenant sessions to rewrite platform Permissions

The security migration grants `SELECT, INSERT, UPDATE, DELETE` on every public table to `indicate_runtime` (`drizzle/0001_stage2_security.sql:219-226`). The `permissions` RLS policy permits every row whose scope is `platform` in both `USING` and `WITH CHECK`, independently of tenant context (`drizzle/0001_stage2_security.sql:193-197`). **Confirmed:** the shared runtime login can create, rename, or delete global Permission definitions used for privileged authorization. Split read and write policies so runtime sessions may read platform Permissions but only a separate trusted administration path may mutate them; tenant Permission writes must remain constrained to the current Organization.

## Membership misses are audited as successful role changes

`changeMembershipRole` supplies a hard-coded `succeeded` audit and delegates the update result to the generic mutation wrapper (`src/application/auth/authorization-service.ts:32-53`). The Drizzle transaction returns `false` when the Organization-scoped Membership update changes no row (`src/infrastructure/db/drizzle-tenant-transaction.ts:68-70`), but the wrapper unconditionally appends the success audit and returns an authorized success envelope (`src/application/auth/authorization-service.ts:70-75`). **Confirmed:** absent and cross-Organization-only target Users yield `ok: true, value: false` plus a false success audit; an unavailable Role is not revalidated and reaches the composite foreign-key failure. Revalidate both target Membership and Role inside the transaction and convert either miss to the same non-disclosing denial before mutation or audit insertion.

## PostgreSQL contract coverage stops before production authorization atomicity

The live suite contains two cases: runtime-role RLS plus append-only deletion, and a cross-Organization Site/Domain constraint (`tests/integration/stage2-postgres-live.integration.test.ts:41-68`). It never instantiates `DrizzleTenantTransactionManager` or `DrizzleSeedRepository`; rollback, revocation races, concurrent uniqueness, local identity linkage, Publisher actor FKs, and seed idempotency remain fake-only or source-text checks. **Confirmed:** task 5.11's database behavioral matrix and the production audit-failure atomicity guarantee are not exercised by the CI/provider-runnable PostgreSQL hook. Extend the opt-in service job with the production adapters and required same-Organization success, absent/cross-Organization denial, concurrent conflict, and injected rollback cases.
