# Stage 2 persisted authorization hardening

The follow-up adds reciprocal Telegram/Membership checks, persisted API-key, Telegram, and claimed-job authorization, transaction-time grant locking for every actor class, and an unconditional PostgreSQL 17 CI contract job. The deterministic Stage 2 checkpoint passes with 34 unit, 5 property, 15 deterministic integration, and 7 Playwright tests, with the 11 PostgreSQL cases delegated to the CI service job and only live Supabase left opt-in. Three prior trust-edge blockers are resolved, but one confirmed blocker remains for checkpoint 6: the Telegram coherence constraint still admits a concurrent interleaving. **Watch for:** **confirmed** a Telegram mapping insert can validate the old Membership Role while a concurrent Membership Role update validates the absence of that still-uncommitted mapping, allowing both transactions to commit a mismatched active mapping.

**Verdict**: NEEDS_CHANGES

## High-level view

Authorization now reloads active API-key scopes and expiry, Telegram Mapping/Membership/Role grants, and leased Publishing Job state instead of accepting caller permission claims. Transaction execution revalidates and locks the persisted actor authorization chain, including Membership, Role, and matching Role-Permission rows for user and Telegram actors.

Membership Role changes deactivate existing active Telegram mappings before changing the Role, and the new migration rejects sequential direct changes that would leave an active mapping mismatched. **Confirmed:** the reciprocal trigger checks do not serialize mapping writes with Membership writes, so concurrent operations can each validate a different committed snapshot and leave the relationship incoherent.

The PostgreSQL workflow is unconditional and uses an ephemeral `postgres:17-alpine` service with a test-only URL. Its Telegram regression is sequential, so it cannot detect the remaining write-skew interleaving.

## Telegram/Membership coherence remains vulnerable to concurrent writes

`membership_telegram_mapping_guard` checks active mappings before a Membership Role or status update, while `telegram_mapping_membership_role_guard` checks the Membership before a mapping insert or update. **Confirmed:** neither trigger locks the opposite relation or takes a shared per-Membership transaction lock. A Membership transaction can observe no active mapping and update Role A to Role B while a concurrent mapping transaction still observes Role A and inserts an active Role A mapping; because the mapping foreign keys independently reference `(organization_id, user_id)` and `(organization_id, role_id)`, both commits remain referentially valid.

The production role-change path deactivates mappings in the same transaction, but it does not close this race: a concurrent mapping insert can finish its BEFORE-trigger check against the old Membership, wait behind the Membership row lock during foreign-key enforcement, and then commit after the role change because no three-column Membership/Role constraint is re-evaluated. This violates the atomic coherence required by Requirements 4.26 and 4.29.

Serialize both mutation directions on the same Membership identity, or replace the trigger pair with a constraint strategy that PostgreSQL rechecks at commit. Add a live PostgreSQL case that races mapping activation/creation against `changeMembershipRole` and asserts that one transaction fails or the mapping is inactive and role-consistent afterward; the current live case only changes the role and then attempts reactivation sequentially.
