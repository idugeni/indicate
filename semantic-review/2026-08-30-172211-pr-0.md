# Tenant-scoped Stage 3 business services and CMS workflows

Major Stage 3 adds a shared `TenantBusinessService` for configuration, RBAC, publisher verification, canonical articles, Site assignment, analytics, and auditing, exposed through a protected Next.js CMS route. **Confirmed:** the production Drizzle adapter does not preserve the service's persistence and concurrency guarantees. **Confirmed:** the browser exposes only a create-oriented subset of the required lifecycle, and the mandatory property gate fails. **Watch for:** **confirmed** permission grants can be erased by any Stage 3 mutation; **confirmed** Role and Membership creates acknowledge success without inserting rows; **confirmed** optimistic conflicts are not enforced at the database write; **confirmed** publisher attribution can remain verified after changing; **confirmed** checkpoint 8 is red.

**Verdict**: NEEDS_CHANGES

## High-level view

**Confirmed:** the adapter loads the entire tenant, mutates an in-memory clone, and rewrites every collection. Unrelated mutations consequently rewrite authorization, Role/Membership creates are not persisted, and service-level version checks are not atomic with SQL writes.

**Confirmed:** the CMS route uses the shared service rather than tenant SQL, but the page implements only Domain/Region creation, Publisher creation, Article creation, and Site assignment. Required CRUD, verification, lifecycle, filtering, analytics, settings, and audit controls remain API-only or absent; **likely**, unguarded command refreshes can also race an Active Organization switch.

**Confirmed:** a verified Publisher can change its public attribution label without re-verification, and an Article can carry arbitrary `source` text independent of its linked Publisher. The public content contract therefore cannot treat the returned Article source as verified attribution.

**Confirmed:** multi-Site analytics retain only one Site per Article, no analytics date filter exists, and foreign tenant filter identifiers become empty matches rather than non-disclosing denials. **Confirmed:** denial-audit failures are suppressed.

**Confirmed:** the in-memory integration suite passes, but there is no Stage 3 PostgreSQL adapter contract. Properties 11 and 34 fail because their test inputs do not satisfy the strict command schemas, leaving checkpoint 8 and the intended properties unproven.

<details><summary>Details</summary>

## Critical — Role grants are rewritten by unrelated mutations

Every production mutation deletes and recreates every Role's grants (`drizzle-stage3-repository.ts:95-124`). **Confirmed:** the replacement query selects only Permissions whose `organization_id` equals the tenant (`:112-115`), excluding platform-scoped Permissions whose organization is null. An Article, Domain, or Publisher change can remove grants such as `membership.manage`. Persist only the changed aggregate, and reconcile grants only for an explicit Role update while retaining valid organization- and platform-scoped Permissions.

## High — Role and Membership creates return records that PostgreSQL never creates

The service adds new Roles and Memberships to mutable state and returns success (`tenant-business-service.ts:196-219`). **Confirmed:** production persistence uses `UPDATE` only for both collections (`drizzle-stage3-repository.ts:110-117`); absent rows are not inserted and affected-row counts are ignored, while a success audit can still commit. Add explicit insert paths and verify the target User/Role relation in the same tenant transaction.

## High — Snapshot persistence defeats optimistic concurrency

The service compares `expectedVersion` with an in-memory version (`tenant-business-service.ts:59-60`), but the adapter upserts records using only `(organization_id, id)` (`drizzle-stage3-repository.ts:95-124`). **Confirmed:** no SQL write predicates on the previously read version, so concurrent users can both pass at version N and the later snapshot can silently overwrite the earlier commit, including unrelated records. Use aggregate-specific versioned updates, treat zero affected rows as conflict, and add concurrent PostgreSQL tests.

## High — The protected CMS does not expose the required Stage 3 lifecycle

The page renders only Publisher create, Article create/assignment, and Domain/Region create forms (`cms-workspace.tsx:105-120`). **Confirmed:** it lacks Site/Site Settings, Role/Membership, Publisher verification and affiliation, Category/Author, Article update/archive/restore, combined editorial filters, analytics date filters, and audit filters. The four Stage 3 Playwright scenarios also omit corrected resubmission, verification, Article lifecycle/filtering, analytics empty states, and audit filtering (`stage3-cms-critical-flow.spec.ts:9-44`). Complete these workflows and exercise them through the protected route.

## High — Verified attribution can change without a new decision

Publisher update resets verification only when name, type, or evidence changes (`tenant-business-service.ts:237-241`). **Confirmed:** `attributionLabel` is omitted while public claims emit it directly (`policies.ts:67`), allowing a verified Publisher to replace its displayed attribution and remain verified. Include every public identity/attribution field in re-verification and test the verified-to-unverified transition.

## High — Mandatory Properties 11 and 34 fail

`npm run test:property` fails 2 of 11 files at seed `20260830`. **Confirmed:** Property 11 spreads a returned Article into a strict update DTO, adding server-owned fields; Property 34 permits prefixes ending in `-`, producing invalid hostnames. Counterexamples are `["zhG2  Kop i","K-NS=H|?rN"]` and `["zhg-569-pl-"]`. Correct test command construction/generators without weakening production validation, replay the counterexamples, and keep checkpoint 8 blocked until all properties pass.

## High — Production behavior has no Stage 3 database contract

All six Stage 3 integration cases use `InMemoryStage3Repository`; the only live suite is the Stage 2 PostgreSQL contract (`stage2-postgres-live.integration.test.ts:19,66`), and `test:postgres:live` names only that file (`package.json:32`). **Confirmed:** Role/Membership inserts, permission preservation, version conflicts, RLS scoping, and mutation/audit rollback are never exercised through `DrizzleStage3Repository`; Playwright also uses the in-memory fixture. Add mandatory CI PostgreSQL coverage for the Stage 3 adapter.

## Medium — Article source text is not bound to verified Publisher identity

Article input accepts both a `publisherId` and arbitrary `source` (`schemas.ts:50-60`). **Confirmed:** the service checks only that the Publisher is active and same-tenant, while public selection returns the raw Article. Return a resolved registry attribution projection, or make the Publisher relation—not free-form text—the authority for downstream public claims.

## Medium — Basic Analytics loses Site assignments and has no date dimension

`buildAnalytics` constructs a `Map<articleId, siteId>`, overwriting earlier Sites (`policies.ts:88-94`). **Confirmed:** `articlesBySite` undercounts multi-Site Articles, and `analytics()` accepts no filter (`tenant-business-service.ts:399-400`). Aggregate over active Article Site rows and add validated date filters to the service, route, CMS, and tests.

## Medium — Foreign filter identifiers do not produce a denial

Editorial filters compare supplied IDs directly and return an empty list on no match (`policies.ts:22-30`). **Confirmed:** `listEditorial` never establishes that Region, Site, Category, Publisher, and Author filter IDs belong to the active tenant (`tenant-business-service.ts:322-328`). Resolve supplied tenant resources first and return the same non-disclosing denial for absent and foreign IDs.

## Medium — Active Organization refreshes can commit stale responses

The effect loader aborts on dependency changes, but reusable `load()` has no abort signal or generation check and always calls `setData` (`cms-workspace.tsx:30-37, 53-59`). **Likely:** an old-organization command refresh resolving after a switch can replace the new tenant's data. Bind responses to the current organization/generation or cancel all outstanding requests, then add a delayed-response race test.

## Medium — Denial auditing fails open

The service suppresses every `recordDenied` error and still returns the denial (`tenant-business-service.ts:80-82`). **Confirmed:** protected denials can disappear from the immutable security trail; route-level membership denials also return before this service path. Make failure observable and define a durable fallback that cannot disclose or write the target into a foreign tenant.
