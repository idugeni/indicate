# Stage 2 tenant persistence and authorization foundation

The change adds the Stage 2 PostgreSQL schema, RLS/grant migration, seed reconciliation, Supabase SSR adapter, tenant authorization services, deterministic fakes, and tests. The intended boundary is a transaction-local Organization context backed by composite foreign keys and append-only audit records, with Supabase identities linked locally before Membership/RBAC checks. The deterministic gate passes, but production wiring and database enforcement paths remain incomplete. **Watch for:** **confirmed** the pooled `postgres` session never assumes the restricted runtime role, **confirmed** production CMS requests do not perform local identity/Membership/Active Organization resolution, **confirmed** a deployable fixed-cookie E2E authentication bypass remains in the CMS route, and **confirmed** mutation/audit atomicity is only demonstrated by the memory fake.

**Verdict**: NEEDS_CHANGES

## High-level view

The migration creates composite Organization foreign keys, forced RLS, and an append-only audit trigger. **Confirmed:** runtime configuration mandates the Supabase `postgres` pool login while no code executes `SET ROLE indicate_runtime`, so the restricted grants and RLS posture are not the effective runtime boundary; broad runtime grants also leave migration metadata writable.

Supabase SSR verifies a remote user, but the production CMS stops at displaying that identity. **Confirmed:** local User linkage, Membership resolution, server-authorized organization switching, and permission reload are not wired into the route, while the Playwright path substitutes hard-coded organizations and a known cookie in production code. **Confirmed:** the callback accepts backslashes in `next`, allowing an encoded value to redirect off-origin after authentication.

User RBAC reloads persisted Membership permissions, but other actor types do not. **Confirmed:** API key and Telegram actors retain caller-supplied Organization and permission sets without verification of key status/scopes or an active Telegram mapping.

The transaction manager installs tenant context and appends audit rows in one Drizzle transaction. **Confirmed:** its port exposes no transaction-bound mutation capability, and authorization occurs before the transaction, so database mutations cannot currently share the audit transaction or recheck a concurrently revoked Membership.

**Confirmed:** application startup and CI do not invoke the database schema assertion, and the Stage 2 “integration” tests inspect SQL strings and memory fakes rather than executing migrations, RLS, grants, constraints, concurrency, or rollback against PostgreSQL.

**Confirmed:** Publisher submitter/verifier IDs have no same-Organization referential constraints, and seed failures emit only a generic category even though the contract requires created/updated/unchanged/failed counts.

<details><summary>Details</summary>

## Supabase callback can redirect authenticated users off-origin

`safeNextPath` accepts values beginning with `/` except `//` (`app/auth/callback/route.ts:7-8`) and feeds the result to `new URL` (`app/auth/callback/route.ts:27`). **Confirmed:** `next=/%5C%5Cevil.example/path` decodes to `/\\evil.example/path`, passes the check, and resolves to `https://evil.example/path`. Reject backslashes and validate the parsed destination's origin, or allow only normalized application paths.

## Fixed-cookie E2E authentication bypass is deployable

The CMS switches authentication branches when `STAGE2_E2E_MODE === '1'` and accepts the constant cookie `stage2-valid` (`app/cms/page.tsx:11-13`). **Confirmed:** production application code contains this bypass without a test-runtime or non-production guard. Remove it from the route and inject a fake at the test boundary, or reject the flag outside an explicit test process.

## Supabase identity never reaches production Membership/RBAC resolution

The live CMS branch verifies the cookie session and uses only `identity.displayName` (`app/cms/page.tsx:30-32`). Repository-wide usage shows `resolveAuthenticatedUser`, `DrizzleAuthorizationRepository`, and `ActiveOrganizationService` are not instantiated by production adapters. **Confirmed:** authentication does not link the local User, verify Membership, load authorized organizations, or establish a server-side Active Organization. The switching flow instead receives E2E-only hard-coded organizations (`app/cms/page.tsx:35-42`) and checks them client-side.

Wire the route through verified identity linkage, derive choices from active Memberships, execute switching server-side, and reload permissions and tenant data after every switch.

## API key and Telegram actors trust pre-populated claims

`AuthorizationService` starts from `actor.permissionSet` and replaces it from persistence only for `actorType === 'user'` (`src/application/auth/authorization-service.ts:20-24`). The repository has no API-key or Telegram verification methods (`src/ports/authorization-repository.ts:4-7`). **Confirmed:** key revocation/expiry/scopes and Telegram mapping/Membership/Role status are not revalidated. Add actor-specific resolvers and reject raw non-user contexts before `authorize`.

## Restricted runtime role is never made effective

The migration creates `indicate_runtime` as `NOLOGIN` and grants it tenant-table privileges (`drizzle/0001_stage2_security.sql:213-224`). Configuration requires `postgres.<projectRef>` for pooled access (`src/config/schema.ts:138`), and no connection or transaction executes `SET ROLE indicate_runtime`. Merely granting the restricted role to the pooled login, as suggested in `docs/MIGRATIONS.md:19`, does not remove `postgres` ownership/BYPASSRLS privileges.

**Confirmed:** forced RLS and audit mutation revocations are not dependable for the configured runtime session. Use a dedicated non-owner, non-BYPASSRLS login or safely assume and validate the restricted role on every connection.

The all-table grant includes `indicate_schema_migrations` (`drizzle/0001_stage2_security.sql:221`). **Confirmed:** an effective runtime session can forge or delete versions consumed by `db:check`. Revoke writes and grant only required reads.

## Mutation and audit atomicity has no production transaction path

`executeAuthorizedMutation` authorizes, then opens a transaction, invokes `mutate`, and appends audit (`src/application/auth/authorization-service.ts:44-49`). `TenantTransaction` exposes only context and `appendAudit` (`src/ports/tenant-transaction.ts:13-17`), not transaction-bound queries or repositories. **Confirmed:** no production path lets a tenant mutation use the audit transaction; the memory fake's global snapshot is why rollback tests pass.

Authorization also completes in separate repository transactions. **Confirmed:** a Membership or Role revoked between authorization and mutation leaves a stale authorized context that proceeds because RLS checks only Organization context. Put authorization, mutation, and audit in one transaction with transaction-bound repositories and suitable locking/consistency.

## Schema-version activation gate is optional

`assertSchemaVersion` exists (`src/application/deployment/schema-gate.ts:17-22`), but instrumentation calls only `getRuntimeConfig()` (`instrumentation.ts:2-5`). `test:stage2` omits `db:check`, and CI still runs `test:stage1` (`package.json:33-34`, `.github/workflows/stage1-quality-gate.yml:23`). **Confirmed:** deployment can start against an absent or partial Stage 2 schema. Invoke the assertion during readiness and add a mandatory pooled-path promotion check.

## PostgreSQL defenses are tested as text, not behavior

The Stage 2 integration suite reads SQL files and checks fragments (`tests/integration/stage2-persistence-auth.integration.test.ts:1-13,38-67`); tenant behavior uses `InMemoryStage2Database`. No test executes a PostgreSQL client, `DrizzleTenantTransactionManager`, or `DrizzleSeedRepository`. **Confirmed:** migrations, composite constraints, RLS roles, append-only defenses, advisory-lock concurrency, identity linkage, and database rollback are unverified. Add an ephemeral PostgreSQL target with separate migration/runtime roles and same-tenant, absent/cross-tenant, concurrent, RLS, append-only, and rollback cases.

## Publisher actor references are not tenant-coherent

`submitted_by` and `verified_by` are unconstrained UUIDs (`src/infrastructure/db/schema/editorial.ts:53-56`). **Confirmed:** PostgreSQL accepts nonexistent or cross-Organization actors. Add composite tenant-safe references through Membership or an equivalent verifier relation, plus absent/cross-tenant integration cases.

## Seed failure reports omit required counts

Success always returns `failed: 0` (`src/application/seed/reconcile-mvp-seed.ts:101`), while the catch path emits only `seed_reconciliation_failed` (`scripts/seed-mvp.ts:27-29`). **Confirmed:** operators receive none of the required counts on failure. Return a sanitized deterministic failure report after rollback and define whether failed-run metadata is persisted separately.
