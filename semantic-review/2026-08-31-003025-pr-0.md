# Stage 7 production-readiness and release gate

This change adds configuration-derived three-root/three-region fixtures, a read-only production readiness command, matrix tests, release/rollback policies, and a consolidated quality gate. Provider inspection covers exact Cloudflare zones and routes, Full (strict) TLS, exact Vercel associations, private R2 exposure, and active database mappings without production writes. Promotion evidence is not yet trustworthy because the live mapping query conflicts with forced RLS and the acceptance matrix is disconnected from deployed persistence. **Watch for:** **[critical, confirmed]** the runtime role cannot see active mappings; **[high, confirmed]** the 3x3 result joins independent in-memory systems rather than a production journey; **[high, confirmed]** the release command bypasses the formal promotion decision; **[high, confirmed]** Telegram webhook-secret correctness is not inspected.

**Verdict**: NEEDS_CHANGES

## High-level view

The production command emits stable categories instead of raw dependency failures. Its database probe opens the pooled `indicate_runtime` connection and joins forced-RLS tenant tables without tenant context, so a correctly secured database cannot return the twelve required mappings.

Cloudflare authority, proxy state, Full (strict), Cloudflare-fronted HTTPS, exact Vercel association, and R2 public-domain state are checked through read-only provider calls. Telegram readiness only compares the Bot API webhook URL and does not prove which secret token the deployed webhook enforces.

The nine-scenario test exercises application services, but publication and public rendering use separate repositories whose public content is already seeded. Cache evidence is a generated key, credential isolation is absent, and CI adds neither a Stage 7 live-Postgres contract nor a full readiness-adapter contract.

`decidePromotion` is not invoked by the executable release path. Rollback safety is also collapsed into caller-provided booleans and proves only queued plus invalidation work, not every durable recovery family named by the runbook.

## Active mapping inspection cannot cross forced RLS

**[critical, confirmed]** `ProductionReadinessAdapter.database()` uses `createRuntimeDatabase(config)` and directly selects from `sites`, `organizations`, `domains`, and `regions` (`src/infrastructure/deployment/production-readiness-adapter.ts`, around lines 143–174). Those tables use forced `tenant_isolation`; `indicate_runtime` is `NOBYPASSRLS` and sees rows only after `app.organization_id` is set (`drizzle/0001_stage2_security.sql`, lines 172–211). The probe establishes no tenant context, and one context could not span the three expected organizations. A correctly secured database therefore returns no mappings and fails `active_database_mappings` even when all twelve sites are active.

Use a tightly scoped read-only `SECURITY DEFINER` discovery function for the exact configured host set, or call the existing exact public-host resolver per host and verify coherence. Exercise that boundary in a live PostgreSQL Stage 7 contract as `indicate_runtime`.

## The 3x3 matrix does not connect publication to public delivery

**[high, confirmed]** The matrix publishes through `InMemoryStage4Repository`, then reads a separate `createStage5E2eRepository(config)` containing pre-published articles (`tests/integration/stage7-acceptance-matrix.integration.test.ts`, around lines 78–177). Public selection can pass even if publication never exposes an article through shared persistence. Isolation compares generated IDs across pre-partitioned data, while cache coverage only asserts distinct `createCacheIdentity` strings rather than trying a foreign cache entry.

There is also no API-key/credential scenario, and Stage 7 Playwright covers only fixture-backed public HTML/SEO. Use one migrated acceptance database and actual composition: publish through an entry point, then observe public content, media, foreign cache rejection, analytics, Telegram projections, audit/job scoping, and credential denial across all nine scenarios.

## Readiness adapter behavior is absent from live CI coverage

**[high, confirmed]** The readiness integration test overrides every database/provider probe (`tests/integration/stage7-production-readiness.integration.test.ts`, lines 8–49). CI runs existing Stage 2/4/5/6 PostgreSQL contracts and `test:providers:stage6`, but no Stage 7 PostgreSQL test and no full HTTP/DNS contract for `ProductionReadinessAdapter` (`.github/workflows/stage2-quality-gate.yml`, lines 20–43). The forced-RLS failure is therefore invisible while all new tests pass.

Add a runtime-role Stage 7 PostgreSQL test with three organizations and twelve sites, plus faithful HTTP/DNS contracts for the composed Cloudflare, Vercel, R2-domain, Telegram-webhook, TLS, and sanitized failure paths. Do not replace the production methods with overrides in those contracts.

## Telegram readiness proves URL, not webhook-secret enforcement

**[high, confirmed]** `telegramWebhookMatches()` calls `getWebhookInfo` and compares only `result.url`; readiness combines that with `getMe` health (`src/infrastructure/deployment/production-readiness-adapter.ts`, around lines 125–135 and 184–190). `config.telegram.webhookSecret` is never consumed, so installation without `secret_token`, or with a stale secret, passes when the URL matches.

Add a non-mutating authenticated probe against the deployed webhook boundary, or compare a non-secret installation fingerprint/version. Prove both acceptance of the configured secret and rejection of a mismatch without tenant mutation.

## The formal promotion decision is not executable release logic

**[high, confirmed]** `decidePromotion()` requires readiness, a nine-scenario report, and the exact diagnostic set (`src/application/stage7/release-gate.ts`, lines 23–39), but only tests call it. `release:stage7` merely chains `test:stage7` and `readiness:production`; the quality script emits diagnostics and the matrix report is never serialized or combined with readiness (`package.json`, lines 50–51; `scripts/run-stage7-gate.mjs`, lines 1–31).

Collect the matrix report, complete diagnostics, and production-readiness report, invoke `decidePromotion`, and emit one sanitized promotion decision/evidence artifact. Shell exit status can remain an outer fail-closed guard.

## Migration readiness can accept an incomplete applied sequence

**[medium, confirmed]** Local readiness checks journal count, indices, and file presence; database readiness reads only `max(version)` (`src/infrastructure/deployment/production-readiness-adapter.ts`, around lines 66–83 and 149–152; `src/application/stage7/production-readiness.ts`, lines 89–91). Version 12 with a missing earlier migration or mismatched name/checksum satisfies `schema_version`, and local SQL is not tied to applied rows.

Compare the full required ordered manifest—version, name, and reviewed checksum/fingerprint—to the applied migration table before accepting `actual >= required`.

## Rollback recovery evidence covers only two durable families

**[medium, confirmed]** `validateRollback()` trusts one `durableWorkResumable` boolean, derived in its integration test from one Redis item and one invalidation task (`src/application/stage7/release-gate.ts`, lines 41–48; `tests/integration/stage7-promotion-rollback.integration.test.ts`, around lines 26–63). Activation attempts, cleanup tasks, transition receipts, expired leases, and webhook outcomes named by Task 15.4/runbook are not reclaimed and completed.

Represent evidence per durable work family and run each real reconciler across a schema-compatible rollback fixture. Fail rollback when any required family is not resumable.

## Secret scanning omits common secret-bearing artifacts

**[medium, confirmed]** `check-stage7-policy.mjs` scans executable source roots, then limits repository-wide inspection to `.json`, `.txt`, `.log`, `.yml`, and `.yaml` (around lines 17–20, 31–37, and 73–79). It skips `.env*`, `.pem`, `.key`, `.p12`, shell files, Markdown artifacts, and source fixtures outside executable roots; the negative test passes only because its directory is injected as an executable root.

Scan secret-bearing environment/key/certificate formats and all committed fixture/source formats, with explicit exclusions for known sentinels. Add negative fixtures for each artifact class.
