# Stage 2 tenant authorization and persistence checkpoint

The current tree implements the Stage 2 schema, migrations, seed reconciliation, Supabase identity linkage, restricted runtime role, tenant transactions, RBAC, and test layers. The four blockers from the preceding review are addressed, and the deterministic checkpoint passes with 33 unit, 5 property, 15 integration, and 7 Playwright tests; eight PostgreSQL and one Supabase external-contract cases are skipped without opt-in services. The remaining gaps are concentrated in persisted actor coherence and revocation behavior. **Watch for:** **confirmed** Membership role changes can leave Telegram mappings pointing at a Role the Membership no longer has, **confirmed** API-key and Telegram actors have no persisted resolver and are always denied, and **confirmed** concurrent Role deactivation or Role-Permission removal can race past the in-transaction authorization recheck.

**Verdict**: NEEDS_CHANGES

## High-level view

Telegram mapping coherence is enforced only when the mapping itself is written. **Confirmed:** changing the referenced Membership's Role does not revalidate or constrain existing mappings, so a Stage 2 Membership mutation can leave persisted Telegram authorization state internally inconsistent.

Authorization ignores caller-supplied permissions and accepts persisted user Membership grants. **Confirmed:** it rejects every API-key, Telegram, and system actor before consulting persistence, so task 5.7 and the valid-actor side of Requirements 6.6 and 6.7 remain incomplete; this is fail-closed, not an authorization bypass.

Membership revocation concurrency is covered by the live PostgreSQL suite. **Confirmed:** the transaction locks only the actor Membership while reading Role and Role-Permission state, leaving Role deactivation and grant removal free to commit after the successful recheck and before the protected mutation.

The opt-in PostgreSQL suite covers the four remediated production-adapter paths. **Confirmed:** it has no case for post-update Telegram coherence, persisted non-user actor resolution, or concurrent Role/Role-Permission revocation, allowing the remaining trust-boundary gaps through checkpoint 6.

<details><summary>Details</summary>

## Membership role changes can invalidate Telegram authorization state

`telegram_identity_mappings` has separate foreign keys to `(organization_id, user_id)` on Membership and `(organization_id, role_id)` on Role. `telegram_mapping_membership_role_guard` proves the three values match an active Membership only before a mapping insert or update (`drizzle/0001_stage2_security.sql:73-93`). **Confirmed:** no reciprocal constraint runs on Membership changes, and `changeMembershipRole` updates only `memberships.role_id` (`src/infrastructure/db/drizzle-tenant-transaction.ts:84-89`). A User mapped to Role A can therefore be moved to Role B while the mapping remains active with Role A, violating Requirements 4.26 and 4.29.

Make `(organization_id, user_id, role_id)` a stable referenced key for Telegram mappings, or transactionally update/deactivate affected mappings whenever a Membership Role or status changes. Add a live PostgreSQL case that changes the Membership through `AuthorizationService` and proves a mismatched active mapping cannot commit.

## Persisted non-user actor resolution is absent

`AuthorizationService.authorize` denies unless `actor.actorType === 'user'`, then reloads only Membership permissions (`src/application/auth/authorization-service.ts:17-25`). `AuthorizationRepository` and its Drizzle adapter expose no API-key status/scope, Telegram mapping, or claimed-job resolver. **Confirmed:** valid non-user actors cannot produce an authorized tenant context, despite task 5.7 requiring Organization derivation from those persisted trust records and the Stage 2 RBAC property claiming Requirements 6.6 and 6.7.

Implement actor-specific resolvers that derive Organization and effective scopes from persisted active records. Extend property and PostgreSQL coverage with valid, revoked, expired, cross-Organization, and role-mismatched cases.

## Role and grant revocation can race the authorization recheck

`revalidatePermission` joins Membership, Role, Role Permission, and Permission, but locks only `memberships` (`src/infrastructure/db/drizzle-tenant-transaction.ts:32-54`). **Confirmed:** Membership status and assignment changes serialize with the mutation, but a concurrent `roles.active` update or `role_permissions` deletion does not. Either revocation can commit after the query returns true while the protected mutation and success audit continue under the stale grant.

Lock the actor Role and matching Role-Permission row alongside the Membership, or use an isolation/predicate strategy that makes grant changes conflict with the protected transaction. Run separate live cases for Membership revocation, Role deactivation, and Role-Permission removal; all three must leave target and audit state unchanged.

## Checkpoint evidence misses the remaining trust edges

The deterministic `npm run test:stage2` pass is reproducible, and the opt-in PostgreSQL file contains eight production-database cases. **Confirmed:** the main run skips all eight without `TEST_DATABASE_URL`, while the live file does not cover Telegram drift, non-user actor resolution, or Role/Role-Permission revocation. Tasks 5.7, 5.10, and 5.11 therefore lack behavioral evidence for required persisted authorization relations.

Add the missing actor and concurrency cases to `stage2-postgres-live.integration.test.ts` and generated property coverage. Require the live PostgreSQL job in every environment that can promote Major Stage 2.
